# Registo de decisões técnicas (ADR)

| # | Decisão | Alternativas | Motivo |
|---|---|---|---|
| D1 | Monólito modular Next.js + worker separado | Microserviços | Menos custo operacional; limites de módulo permitem extrair depois |
| D2 | **Drizzle ORM** (+ `postgres-js`) | Prisma | Tipos fortes sem gerar cliente/binários; SQL explícito facilita RLS e `set_config`; bom com Supabase pooler |
| D3 | Multi-tenant em schema partilhado + `organization_id` + RLS | BD/schema por tenant | Escala para milhares de restaurantes com operação simples; RLS como segunda barreira |
| D4 | Tenant = organização (NIF), com N estabelecimentos | Tenant = restaurante | Grupos com várias casas; faturação da comissão é à empresa |
| D5 | Dinheiro em cêntimos inteiros; taxas em pontos base | `numeric`/floats | Sem erros de vírgula flutuante; aritmética exata |
| D6 | Comissão acumulada em unidades de 1/10 000 cêntimo e arredondada uma vez no extrato | Arredondar por pedido | Evita perda sistemática de cêntimos em pedidos pequenos |
| D7 | Base de comissão por defeito: **sem IVA** | Com IVA | Requisito do negócio; configurável por regra |
| D8 | Tokens de mesa aleatórios (128 bits) guardados em BD | Tokens assinados (HMAC) | Revogáveis individualmente, sem chaves a gerir; URLs curtos |
| D9 | ~~Transactional outbox + BullMQ~~ — substituída por D15 | Enviar ao POS no pedido HTTP | Garante zero perdas mesmo com Redis/POS em baixo |
| D10 | Capacidades declaradas por adaptador POS | Assumir funcionalidades | Não inventar a API ZoneSoft; degradação controlada |
| D11 | Tailwind v4 sem fontes externas | next/font Google | Sem dependências de rede em build; rapidez em rede móvel |
| D12 | Vitest para testes unitários; Playwright para E2E (Fase 2) | Jest | Rápido, ESM nativo, compatível com Vite/TS |
| D13 | Sem ESLint na Fase 1 | Configurar já | Next 16 removeu `next lint`; configuração flat do ESLint entra na Fase 2 com a CI |
| D14 | Fase 1 sem BD: diretório de mesas em memória (`TableDirectory`) | Exigir Postgres já | Projeto arranca com `npm run dev`; a interface é a mesma que a implementação Drizzle da Fase 3 |
| D15 | Fila de envio ao POS e rate limit **no próprio Postgres** (outbox com `FOR UPDATE SKIP LOCKED` + lease; contadores por janela com upsert) | BullMQ + Redis | Menos uma peça que pode falhar ou custar dinheiro; o pedido e a tarefa ficam na mesma transação sem relay; volume esperado (centenas de pedidos/hora por restaurante) está muito abaixo do limite do Postgres. Rever se a fila passar de ~50 tarefas/s |
| D16 | **PGlite** (Postgres em WebAssembly) em desenvolvimento e testes; Supabase em produção | Docker/Postgres local obrigatório | `npm run dev` funciona sem instalar nada; os testes correm contra Postgres verdadeiro (mesmas migrações e SQL) |
| D17 | Worker no próprio servidor Node (`instrumentation.ts`), com alternativa `/api/cron/outbox` para serverless | Processo separado obrigatório | Um só processo a gerir no início; em Vercel usa-se o cron. Envio imediato após o pedido para o cliente ver "Confirmado" em segundos |
| D18 | ~~Acesso ao painel por código do restaurante~~ — substituída por D21. Acesso ao painel por **código do restaurante** (scrypt) + cookie assinado (HMAC, 12 h), com rate limit no login e verificação de origem nas ações | Supabase Auth já | Permite piloto sem contas individuais. Limitação: não sabemos *que* funcionário fez cada ação (a auditoria regista o restaurante). Substituir pela Supabase Auth com perfis owner/manager/staff antes de vários restaurantes |
| D19 | Painel em "tempo real" por **polling a cada 3 s** | SSE / WebSockets / Supabase Realtime | Funciona em qualquer alojamento (incluindo serverless) e em redes fracas, sem ligações persistentes; custo baixo (uma consulta por tablet a cada 3 s) |
| D20 | Esgotados do painel guardados por referência do POS, aplicados por cima do catálogo do POS (só podem tirar artigos, nunca repor) | Editar o catálogo | O POS continua a ser a fonte de verdade; não é preciso sincronizar o catálogo para a BD primeiro |
| D21 | **Supabase Auth** com entrada por **código de 6 dígitos por email** (OTP), só para utilizadores convidados (`shouldCreateUser: false`); perfis dono/gerente/staff em `memberships` | Password; magic link | Sem passwords para gerir nem repor; o código funciona num tablet partilhado da cozinha (o link abriria noutro dispositivo). A sessão é validada com `getUser()` no servidor e renovada no `proxy.ts` |
| D22 | **RLS com role `app_user` + `withTenant`** em cada pedido; funções `SECURITY DEFINER` mínimas para resolver token de mesa e associações | Filtrar só no código | Segunda barreira: um bug numa consulta não expõe dados de outro restaurante. Testado com uma segunda organização |
| D23 | Modo de desenvolvimento sem Supabase: escolher um utilizador de demonstração (cookie assinado). Desligado em produção | Exigir Supabase em dev | Permite testar perfis e permissões sem conta externa; em produção, sem Supabase configurada, o painel recusa entradas |
| D24 | Resultado **ambíguo** do POS (`unknown`: timeout/exceção) só é reenviado se o adaptador declarar `externalIdempotencyKey`; senão vai ao staff verificar | Reenviar sempre | Entrega "pelo menos uma vez" duplicava pedidos na cozinha em POS sem deduplicação (auditoria F1) |
| D25 | **Um pagamento ativo por conta**, com a sessão bloqueada; reconciliação dos pendentes pelo worker; fecho da mesa recusado com dinheiro em curso | Deixar vários pendentes | Evita pagar a mais e cobrar duas vezes (auditoria P1–P3) |
| D26 | Catálogo do POS em **cache de 30 s por restaurante** (com último bom em caso de falha); esgotados do painel sempre da BD | Pedir ao POS em cada visita | Limites de pedidos do POS e resiliência (auditoria X1); passo intermédio até sincronizar o catálogo para a BD |
| D27 | IP do cliente só do cabeçalho do **proxy de confiança** (`TRUSTED_PROXY`) | Primeiro cabeçalho que existir | Cabeçalhos não reescritos pelo proxy são forjáveis (auditoria S2) |
| D28 | **Modo por lugar**: `pay_later` (mesas, paga a conta no fim) ou `pay_first` (espreguiçadeiras/balcão, paga cada pedido ao pedir). O pedido pré-pago nasce `AWAITING_PAYMENT` e só entra na outbox quando o pagamento é confirmado (por quem detetar primeiro: cliente, worker ou webhook, com compare-and-set) | Exigir pagamento antes de criar o pedido | O pedido fica registado e visível ("por pagar"), o valor fica fixado no servidor, e um pagamento abandonado cancela o pedido aos 15 min sem nunca chegar à cozinha. O limite de 150 € não se aplica: o pagamento prova que o pedido é real |
